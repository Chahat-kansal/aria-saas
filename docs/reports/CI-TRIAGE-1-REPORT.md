## Part 3 — the suspicious 8-second "success" (run `29222447113`)

- Workflow: **Deploy to Vercel on Push**, event `push`, `head_sha 4162ef49`, 2026-07-13T03:47:31Z → 2026-07-13T03:47:39Z (8 seconds).
- Full job/step breakdown: `Set up job` → `Trigger Vercel Deploy Hook` → `Complete job`. Exactly **one** substantive step: `curl -X POST "https://api.vercel.com/v1/integrations/deploy/prj_ttjBzoTEUmYGnhhim8mX23GiJth7/AwbWuGaxxB"`.
- **It verified nothing.** No `npm ci`, no `tsc`, no `next build`, no tests. It is a fire-and-forget webhook ping that tells Vercel "start a deploy" — Vercel then runs its own independent build using its own Git integration, completely outside this workflow's visibility. A green checkmark on this workflow has never meant "the app builds" or "tests pass" — only "the HTTP request to Vercel's webhook succeeded." This is the short-circuit the 8-second runtime suggested.

## Per-workflow purpose / redundancy / cost (from reading each YAML)

- **`deploy.yml`** — sole purpose is pinging a Vercel deploy hook. **Fully redundant** with Vercel's own Git-push deploy integration (confirmed independently: every deployment this session reached `READY` via Vercel's own pipeline, triggered by the same `git push`, with or without this Action running). Cost: ~1 min/run × every push, forever, for a duplicate trigger.
- **`e2e.yml`** — `typecheck` + `e2e-local` (full local Playwright suite against a built dev server) on every push/PR, plus a `test` job that runs a *different*, pre-existing prod-smoke check triggered by `repository_dispatch` on a successful Vercel deploy (unrelated to Vercel's own building — genuinely additive verification against the live site). Real, valuable coverage; currently the most expensive and least reliable workflow.
- **`smoke.yml`** — security-focused regression suite (RULE 13) for auth/routing/middleware/RLS changes, PR-triggered only. Genuinely valuable, currently **inert** (0 runs ever) because this repo never uses PRs.
- **`canon-rail-guard.yml`** — a pure git-diff pattern scanner (no build/test), recently fixed to trigger on push. Cheapest workflow with real content by far.

## Recommendation

1. **Delete `deploy.yml` immediately** — zero unique value, redundant with Vercel's native integration, and its false-green history (100% "success" while verifying nothing) is actively misleading about deploy health.
2. **Fix `smoke.yml`'s trigger** the same way Canon Rail Guard's was fixed (add a `push: branches: [main]` trigger, keep the existing `paths:` filter) — it currently provides none of its intended security-regression coverage.
3. **Fix `e2e.yml`**, in priority order: (a) fix the ambiguous "Sign in" locator — this is the actual reason the workflow has stayed red since the OOM fix landed; (b) re-verify all 6 required secrets are genuinely set in Actions → Secrets (the missing-`supabaseUrl` failure suggests they weren't reliably present at least once); (c) add `NODE_OPTIONS` to any other memory-heavy step in this workflow (currently only the `typecheck` job has it); (d) add a `paths:` filter so it doesn't burn ~34 minutes on commits that touch no app code.
4. **Keep `canon-rail-guard.yml`** as-is (already fixed and cheap).
5. **Whether 2,000 free minutes is enough once trimmed**: deleting `deploy.yml` removes a small, constant per-push cost (~1 min × every push). The real lever is fixing `e2e.yml` to actually pass (avoiding wasted retries) *and* adding a `paths:` filter to it — without the filter, even a perfectly green E2E suite still costs ~34 minutes on every push regardless of content, and this repo's own commit cadence (10+ pushes in a single working session has been observed) means that alone can approach or exceed 2,000 minutes within a single active month. **With a `paths:` filter added, 2,000 minutes is very likely enough** for a repo this size; **without one, it is not**, however many other fixes land.
